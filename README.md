# Алхам 3: Сценарио бүрээс SLO гаргах

| Сценарио     | SLI (юуг хэмжих)                            | Босго                      | Цонх / нөхцөл                              |
| ------------ | ------------------------------------------- | -------------------------- | ------------------------------------------ |
| Performance  | `/cart/add` latency                         | p95 < 200 мс, p99 < 400 мс | 20 VU, ойролцоогоор 10 хүсэлт/сек, 1 минут |
| Reliability  | `/pay` error rate                           | < 8%                       | 20 VU, 1 минут                             |
| Availability | Бүх хүсэлтийн амжилтын хувь + recovery time | ≥ 90%, recovery ≤ 10 сек   | 2 минутын тест, 10 секундийн зогсолт орсон |
| Нэмэлт (4-р) | `/report` latency                           | p95 < 450 мс               | 20 VU тогтмол ачаалалд, 1 минут            |

## Босго сонгосон үндэслэл

* **Performance:** `/cart/add` нь localhost орчинд ажиллаж байгаа тул хариу өгөх хугацаа харьцангуй бага байх ёстой гэж үзэж, p95 < 200 мс, p99 < 400 мс гэсэн эхний босгыг сонгосон. Алхам 4-ийн бодит тестийн үр дүнгээр дахин шалгана.
* **Reliability:** `/pay` endpoint-д ойролцоогоор 5% алдаа гарахаар тохируулсан гэж үзвэл тестийн үед санамсаргүй хэлбэлзэл гарах боломжтой. Тиймээс 8%-ийг бодитой, шалгаж болох босго болгон сонгосон.
* **Availability:** Тестийн үед серверийг зориудаар 10 секунд зогсоох тул recovery time-ийг 10 секундээс ихгүй байхаар тодорхойлсон. Нийт хүсэлтийн дор хаяж 90% нь амжилттай байх шаардлага тавьсан.
* **Нэмэлт (4-р, report):** `/report` endpoint нь `server.js`-д кодоороо 200–400мс хооронд санамсаргүй хугацаагаар хариулдаг тул хамгийн муу тохиолдолд ~400мс болно. Тиймээс 450мс threshold нь бага зэрэг margin өгсөн, бодитоор хэмждэг тоо.

## Availability Error Budget

Availability SLO нь **≥ 90%** бөгөөд тестийн цонх **2 минут** байна.

2 минут = 120 секунд

Зөвшөөрөгдөх downtime: **120 × (1 - 0.90) = 12 секунд**

Тиймээс 2 минутын цонхонд хугацаагаар тооцсон availability error budget нь **12 секунд**. Энэ нь сервер нийтдээ 12 секунд хүртэл зогсож болох гэсэн үг. Харин тестийн нөхцөлд серверийг 10 секунд зориудаар зогсоож байгаа тул хугацаагаар тооцсон error budget дотор багтана.

Гэхдээ сервер зогссон үед хүсэлтүүд connection refused зэрэг шалтгаанаар маш хурдан амжилтгүй болж болох тул **хугацаагаар тооцсон 12 секундийн error budget болон хүсэлтийн тоогоор тооцсон error budget хоёр ижил гарах албагүй**. Алхам 5-д бодит хүсэлтийн тоо болон амжилтгүй хүсэлтийн тоог ашиглан дахин тооцож харьцуулна.

# Алхам 4: SLO-гоо k6 threshold болгох

`slo-test.js` файлд endpoint бүрийг `tags: { name: ... }`-аар ялгаж, дараах threshold-уудыг тохируулав:

```javascript
export const options = {
  vus: 20, duration: '1m',
  thresholds: {
    'http_req_duration{name:cart}':   ['p(95)<200'],   // Performance SLO
    'http_req_failed{name:pay}':      ['rate<0.08'],   // Reliability SLO
    'checks':                         ['rate>0.90'],   // Availability SLO
    'http_req_duration{name:report}': ['p(95)<450'],   // Нэмэлт (4-р) SLO
  },
};
```

Ажиллуулсан: `k6 run slo-test.js 2>&1 | tee results/pass.txt`

## Гарсан үр дүн (results/pass.txt)

```
THRESHOLDS
  checks
    ✓ 'rate>0.90' rate=98.28%

    http_req_duration{name:cart}
    ✓ 'p(95)<200' p(95)=2.67ms
    ✓ 'p(99)<400' p(99)=25.58ms

    http_req_duration{name:report}
    ✓ 'p(95)<450' p(95)=392.5ms

    http_req_failed{name:pay}
    ✓ 'rate<0.08' rate=5.14%
```

**Бүх 4 threshold PASS.** Ажиглалт:

* `/cart/add` бодит p95 = 2.67мс, p99 = 25.58мс байна. Аль аль нь threshold болох p95 < 200мс, p99 < 400мс-ээс хамаагүй бага байгаа тул localhost орчинд серверийн хариу маш хурдан байгааг харуулж байна.

* `/pay` error rate **5.14%** нь серверт кодоор суулгасан ~5% алдаатай нийцэж, 8% threshold-той сайн зохицож байна.

* `/report` бодит p95 **392.5мс** нь 450мс threshold-той ойрхон, сайн уялдаатай — учир нь энэ тоог сервер кодны бодит хязгаараас (200–400мс) гаргаж авсан.

# Алхам 5: Chaos тест — Availability сценариог бодитоор турших

## Тестийн нөхцөл

- `duration: '2m'` болгож `slo-test.js`-ийг ажиллуулав.
- Тест эхэлснээс хойш ойролцоогоор 30 секундийн дараа сервер процессыг `Ctrl+C`-ээр зориудаар зогсоов.
- Яг **10 секунд** хүлээгээд, `node server.js` командаар серверийг дахин асаав.
- Бүрэн гаралтыг `results/chaos.txt`-д хадгалав.

## Гарсан үр дүн

```
THRESHOLDS
  checks
  ✗ 'rate>0.90' rate=88.04%

  http_req_duration{name:cart}
  ✓ 'p(95)<200' p(95)=2.68ms

  http_req_duration{name:report}
  ✓ 'p(95)<450' p(95)=390.79ms

  http_req_failed{name:pay}
  ✗ 'rate<0.08' rate=14.68%
```

- **Availability threshold FAIL**: checks_succeeded 88.04% (5000/5679) — SLO-д заасан ≥90%-аас доогуур
- **Reliability threshold FAIL**: `/pay` error rate 14.68% (278/1893) — SLO-д заасан <8%-аас өндөр
- **Performance threshold-ууд PASS хэвээр**: `/cart/add` p95=2.68мс, `/report` p95=390.79мс — сервер унасан хугацаанаас гадуурх хүсэлтүүд хэвийн хурдтай хариулсан тул latency threshold дээр нөлөө үзүүлээгүй

Энэ тестийг дахин давтахад (өмнөх туршилт: 88.07%/14.94%, энэ туршилт: 88.04%/14.68%) үр дүн бараг ижил гарсан нь энэ chaos тохиолдол **давтагдах чадвартай (reproducible)** болохыг харуулж байна — санамсаргүй нэг удаагийн зөрүү биш.

## Бодит Availability тооцоолол (хүсэлтээр)

```
Бодит availability = checks_succeeded / checks_total = 5000 / 5679 = 88.04%
```

SLO 90% байсан тул **error budget хэтэрсэн**.

## Цагаар тооцсон vs хүсэлтээр тооцсон budget яагаад зөрдөг вэ?

Алхам 3-т цагаар тооцсон error budget 12 секунд байсан (2 минутын 10% нь). Гэтэл бодит тестэд 10 секунд зогссон ч, availability доголдол 88.04% буюу ~10 секундээс хамаагүй өндөр хувийн доголдол харагдаж байна. Учир нь:

1. Сервер унасан үед хүсэлтүүд **connection refused** алдаагаар шууд, маш хурдан унадаг (`/report` хэвийн үедээ 200-400мс хүлээдэг байсан бол, унасан үед 0мс-д шууд алдаа буцаадаг). Иймд секунд тутамд илгээгддэг хэвийн хүсэлтийн тооноос хамаагүй **олон хүсэлт** зогсолтын секундэд "багтдаг" (connection refused нь маш хурдан буцдаг тул).
2. Мөн серверийг гараар (`node server.js`) дахин асаахад бэлэн болтол (жижиг ачаалах хугацаа, Node.js process эхлэх хугацаа) нэмэлт секунд орж болзошгүй тул бодит "унасан хугацаа" 10 секундээс арай илүү байж мэдэх юм.

Товчхондоо: **цагаар тооцсон budget** нь хугацааны нэгжид тэнцүү жинтэй гэж үздэг байсан бол, **хүсэлтээр тооцсон budget** нь зогсолтын секунд бүрт хэвийнээс олон хүсэлт унадаг тул илүү хатуу (worse) харагдана.

## Reliability threshold яагаад мөн FAIL болов?

`/pay` error rate 5.41%-аас (энгийн тест) 14.68% (chaos тест) болж өссөн. Учир нь сервер бүрэн унасан үед `/pay`-руу илгээсэн хүсэлт бүр **connection refused**-ээр амжилтгүй болдог — энэ нь server.js доторх зориудаар суулгасан ~5% санамсаргүй алдаанаас тусдаа, илүү том шалтгаан юм. Иймд нэг availability эвдрэл (сервер унах) **зэрэг хоёр SLI-г** (availability, reliability) зөрчиж байна — эдгээр хоёр SLI бие биенээсээ бүрэн тусгаарлагдаагүй байгааг харуулж байна.

**Хэрхэн тусгаарлах вэ?** Reliability SLI-г зөвхөн сервер ажиллаж байх үед гарсан application-level (жишээ нь HTTP 500) алдаагаар хэмжиж, харин connection-level алдааг (сервер бүрэн боломжгүй үе) тусад нь зөвхөн availability SLI-д ноогдуулбал хоёр metric илүү цэвэр тусгаарлагдана.

# Алхам 6: Threshold-оо зориуд эвдэх

`/report`-ийн threshold-ыг `p(95)<450` → **`p(95)<50`** болгож `slo-test-fail.js` файлд тусад нь хадгалав (`duration: '1m'`).

Ажиллуулсан: `k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; echo "exit=${PIPESTATUS[0]}"`

## Гарсан үр дүн (results/fail.txt)

```
THRESHOLDS
  checks
  ✓ 'rate>0.90' rate=97.94%

  http_req_duration{name:cart}
  ✓ 'p(95)<200' p(95)=2.51ms

  http_req_duration{name:report}
  ✗ 'p(95)<50' p(95)=388.05ms

  http_req_failed{name:pay}
  ✓ 'rate<0.08' rate=6.15%

level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"
exit=99
```

`/report`-ийн threshold зориудаар FAIL болов (`p(95)=388.05ms` > `50ms`), учир нь сервер өөрөө 200-400мс хооронд л хариулдаг тул 50мс-ээс хурдан хариулах боломжгүй — энэ FAIL нь ямар ч машин дээр найдвартай давтагдана.

**Exit code = 99** (0 биш). Анхны тестэд `$?` ашигласан үед `tee`-ийн exit code (0) буцаж алдаатай харагдсан тул `${PIPESTATUS[0]}` ашиглаж k6-ийн жинхэнэ exit code-ыг олж авсан. Яг энэ exit code-оор CI pipeline build амжилтгүй гэдгийг илрүүлж, build-ийг зогсоодог.

# Дүгнэлт

Энэ лабораторид хамгийн хэцүү зүйл бол сценариог 6 хэсэгтэй форматаар зөв ялгах, тэр дундаа хэмжүүрт тохирсон бодит, шалгаж болохуйц босго тогтоох байлаа. Тоо санамсаргүй сонгохгүйгээр, серверийн бодит зан төлөвт (жишээ нь `/pay` кодонд суулгасан ~5% алдаа) тулгуурлан үндэслэлтэй босго гаргах шаардлагатай байсан нь эхэндээ бэрхшээл учруулсан. SLO-гоо k6 threshold код болгож хөрвүүлэхэд README дэх тоо болон скрипт дэх threshold яг ижил байх ёстой байсан бөгөөд endpoint бүрийг `tags`-аар зөв ялгаж, `http_req_duration{name:...}` гэх мэт нэр өгөх шаардлагатай байв — эсрэг тохиолдолд бүх endpoint-ийн metric холилдож, тодорхой threshold тавих боломжгүй болно. Эхний тестийн үр дүн хүлээлтээс бага зэрэг доогуур (жишээ нь `/cart/add`-ийн p95 хүлээснээс хамаагүй бага) гарсан ч, энэ нь ойролцоогоор зөв хүрээнд байсан тул threshold-оо дахин тохируулах шаардлагагүй болсон.

Chaos туршилт availability сценариогийн хэмжүүрийг хэсэгчлэн батлав, хэсэгчлэн үгүйсгэв. Сервер 10 секунд унасан үед хүсэлтүүд connection refused алдаагаар маш хурдан амжилтгүй болсноос болж, секунд тутамд хэвийнээс хамаагүй олон хүсэлт "унасан" тул бодит availability (88.04%) миний онолоор тооцсон 90%-ийн SLO-оос доогуур гарсан. Энэ нь цагаар тооцсон error budget (12 секунд) болон хүсэлтээр тооцсон бодит зөрчил хоёр яагаад ялгаатай болохыг тодорхой харуулсан — цаг хугацааны нэгжид тэнцүү жин өгсөн онолын тооцоолол бодит систем дэх хүсэлтийн урсгалын онцлогтой давхцдаггүй болохыг ойлгосон. Мөн нэг availability эвдрэл (сервер унах) зэрэг Reliability threshold-ыг мөн зөрчсөн нь эдгээр хоёр SLI бие биенээсээ бүрэн тусгаарлагдаагүй болохыг харуулсан.

Хэрвээ дахин хийвэл, ялангуяа сервер унасан үеийн хүсэлтийн зан төлөвт (connection refused-ийн хурд, дахин асаах хугацаа) илүү нарийвчилсан анхаарал хандуулж, availability болон reliability SLI-г эхнээсээ илүү тодорхой тусгаарлах аргачлал (жишээ нь зөвхөн application-level алдааг reliability-д, connection-level алдааг зөвхөн availability-д тооцох) сонгож эхэлбэл илүү цэвэр үр дүн гарах байсан гэж бодож байна. Ерөнхийдөө энэ лаборатори сценарио → SLO → threshold шилжилтийн онолын дараалал бодит систем дээр яаж хэрэгждэг, мөн онол ба бодит хэмжилтийн хоорондох зөрүү яагаад үүсдэгийг практикт харуулсан хэрэг болсон.
